# opentp-spec: Agent Guide

This repo is the source of truth for the **OpenTrackPlan file format**: JSON Schemas (`schemas/`), normative and reference docs (`docs/`), example tracking plans (`examples/`) and a self-contained consistency checker (`scripts/validate.ts`). It contains no runtime code and has no package dependencies. The reference implementation lives in `opentrackplan/opentp-cli`.

## Rules

- **English only** in code, comments, docs, examples and commit messages.
- **Do not commit, tag or push unless the user asks.** A pushed tag is permanent: jsDelivr caches it as immutable, and the next rule forbids moving it. Run every check before proposing `git tag`.
- **Never move, delete or re-push a published tag** (`2025-06`, `2025-12`, `2026-01`). jsDelivr serves tagged files with `cache-control: ... max-age=31536000, immutable`, so a moved tag never propagates and clients end up with different files.
- **Change things together.** A format change touches `schemas/`, `docs/`, `examples/` and `README.md` in the same change. Docs snippets must match the schemas, and examples must match both.
- **Do not change a published spec version in place on your own.** `2026-01` has been changed in place at least once after it was finalized (`b8bdeae`, 2026-02-03): commit `27b1a4c` (2026-06-20) added `name`/`example` to `field.schema.json` **and** relaxed the normative `valueRequired` rule (a fixed `value` is now required only when the field is required or the event defines it). In-place edits are never served (see "Schema publishing"). The owner decides, and the decision is recorded in `CHANGELOG.md`.
- **Only use JSON-Schema keywords that `scripts/validate.ts` implements** (see the subset below), or extend the validator and add a test in the same change. Any other keyword is ignored without a warning.
- **Keep duplicated schema definitions in sync** (see the recipe "Add or change a Field keyword").
- **Edit docs here, never the website copies.** `opentp-website/src/content/docs/docs/spec/` is generated by that repo's sync scripts.
- Every `examples/**/*.yaml` must be a complete opentp.yaml, event or dictionary file. The validator fails on anything else.
- Prefer the minimal form in docs and examples (implicit payload, unversioned). Show the expanded form only where it is the topic.

## Format model (2026-01, compact)

Common to all schemas:
- They are draft-07 with `$id: https://opentp.dev/schemas/2026-01/<name>.schema.json`. Cross-file `$ref`s are relative file names (`version.schema.json`, `field.schema.json`), so they resolve against `$id`.
- Every file has a top-level `opentp: YYYY-MM`.
- Almost every object is `additionalProperties: false`. That includes the root, so a `$schema:` key inside YAML is an error. Use the comment `# yaml-language-server: $schema=...` instead.

### opentp.yaml

```text
opentp*: YYYY-MM
info*:    { title*, version* (string! YAML 1.0 is a number), description, contact: string[] }
spec*:
  paths*:   { events*: { root*, template* }, dictionaries: { root* } }
  targets:  { <targetId>: { title, description, schema: { <field>: Field } } }   # per-target base schema
  events*:
    key:       { minLength, maxLength, pattern, format }        # constraints only, no generation
    x-opentp:  { keygen: { template*, transforms: { <pipelineId>: [step, ...] } } }
    taxonomy*: { <fieldId>: TaxonomyField }                     # may be {}
    payload*:  { targets*: { all*: [targetId...], <selector>: [targetId...] }, schema*: { <field>: Field } }  # schema may be {}
    pii:       { kind: PiiReserved, masker: PiiReserved, schema: { <metaKey>: PiiMetaField } }
```

- **Grammars** for the path template, keygen and PII config: see `docs/schema/opentp-yaml.md`. A `{fieldId}` in the path template matches one path segment (not a regex), and its value joins `event.taxonomy`. Keygen step names are tooling-defined; the spec does not list them.
- **`spec.events.payload.targets`:** `all` is required and reserved, and it is the canonical target-id list. Other keys are selector groups that should only contain ids from `all`. The schema does not enforce `minItems`, uniqueness or the subset rule.
- **`spec.targets` keys** are free strings. The docs say only that they "should match" `targets.all`.
- **TaxonomyField:** requires `title` **and** `type` (`string|number|integer|boolean`). Optional: `description`, `required`, `enum`|`dict` (exclusive), constraints by type (string: `minLength maxLength pattern format`; number/integer: `minimum maximum exclusiveMinimum exclusiveMaximum multipleOf`; boolean: none), and `x-opentp`. A **composite** field uses `template` + `fragments` (both or neither, string only). `fragments` is a map of TaxonomyField, and fragment ids become taxonomy keys. There is no `value`, `example`, `name` or array type.

### Event file

```text
opentp*: YYYY-MM
event*:
  key*:      string (minLength 1), opaque, unique per plan
  lifecycle: { status: active|deprecated|draft, deprecatedAt (date string), deprecatedReason, replacedBy: key }
  taxonomy*: object                      # required even if {}; validated by tooling against spec.events.taxonomy
  aliases:   [ { key*, deprecated: { reason, date } } ]
  ignore:    [ { path*, reason* } ]      # path conventions in docs/schema/events.md ("event.ignore")
  payload*:  Target | { <selectorOrTargetId>: Target }      # minProperties 1
Target          = PayloadVersion | VersionedTarget
PayloadVersion  = { schema*: { <field>: Field }, meta: { changes: string|string[], deprecated: { reason*, date } }, $ref: string }
VersionedTarget = { current*: string, <versionKey>: PayloadVersion, <aliasKey>: "<key>" }   # `schema` key forbidden
```

Deprecation already has three different shapes: `lifecycle` (`status: deprecated`, `deprecatedAt`, `deprecatedReason`, `replacedBy`), `aliases[].deprecated` (`{reason?, date?}`) and `meta.deprecated` (`{reason*, date?}`). Fields have no deprecation keyword.

The three payload forms:
1. **Implicit unversioned:** `payload.schema`.
2. **Implicit versioned:** `payload.current` plus versions and aliases.
3. **Map form:** `payload.<key>`, where each value has shape 1 or 2.

How they apply:
- The implicit forms apply to every id in `targets.all`.
- In map form a key is a selector (including `all`), else a target id in `all`, else an error.
- A target id may be covered at most once per event.
- Partial coverage is accepted in practice (`examples/full/events/onboarding/*` cover only `mobile`), but the spec does not define what an uncovered target means.

Versioning:
- `current` and aliases resolve through aliases to a version key.
- `$ref` is either `"<versionKey>"` or `"<payloadKey>::<versionKey>"` (the second only in map form).
- Aliases are resolved first. Chains are allowed; cycles are errors.
- Only `schema` is inherited (never `meta`), and the result is `merge(refSchema, schema)`.
- An inherited field cannot be removed.
- Every version needs `schema`, even with `$ref` (write `schema: {}`).
- Quote version keys and alias values (`"1.0.0"`).

### Field (`field.schema.json`)

- **Allowed on every field:** `name` (logical/code name; the YAML key stays canonical), `title`, `description`, `required`, `valueRequired`, `value`, `example` (no effect on validation), `pii` (`kind` and `masker` are reserved strings; extra keys are allowed), and `x-opentp` (`role: constant|attribute|shared`, `checks: {}`).
- **Within one definition:** `enum`, `dict` and `value` are pairwise exclusive, and `type` or `value` is required.
- **`format` values:** `date date-time email uuid uri ipv4 ipv6`.

Exactly one `oneOf` branch must match:

| Branch | Allowed constraints | Typing of `enum`/`value`/`example` |
|---|---|---|
| untyped (no `type`) | none: no enum, dict, constraints or items | `value` is any scalar or scalar array |
| `string` | `minLength maxLength pattern format` | strings |
| `number` / `integer` | `minimum maximum exclusiveMinimum exclusiveMaximum multipleOf` | numbers / integers |
| `boolean` | none | booleans |
| `array` | `items` (required) plus `minItems maxItems uniqueItems`. Top-level `enum`/`dict` are forbidden. | `value`/`example` are scalar arrays |

`items` (`definitions.arrayItems`) requires a scalar `type` and takes `enum`|`dict` and scalar constraints. It has no `x-opentp`. `object` is intentionally not a type.

### Dictionaries and extension points

- **Dictionary:** `{ opentp, dict: { type*: string|number|integer|boolean, values*: [...] } }`. `values` has minItems 1, unique items, and items typed per `type`. Values carry no metadata.
- **`x-opentp` is allowed only at:**
  - `spec.events.x-opentp` (`keygen` only);
  - field-level `x-opentp` (`role`, `checks`) on payload Fields, taxonomy fields and fragments, `pii.kind`/`pii.masker` config, and pii meta fields.

  Both containers are closed (`additionalProperties: false`). There are no vendor `x-*` keys, and there is no `x-opentp` on the event root, info, targets, dictionaries, payload versions or array items.
- **`x-opentp.role`** is not consumed by the reference CLI. Masker id `star` is called "built-in" (events.md), but no tool implements masking.

## Normative semantics (`docs/semantics.md`)

- **Layers**, merged in order per target (and per version):
  1. `spec.events.payload.schema`
  2. `spec.targets.<id>.schema`
  3. the event schema for that target/version
- **Text:** fields are merged by name, using a *shallow* merge in which later layers win. The merged result must be a valid Field.
- **Conflicts:** changing `type`, weakening `required`, weakening `valueRequired`, or ending with an invalid merged field (e.g. both `enum` and `value`).
- **`valueRequired: true`** in the effective schema requires a fixed `value` when the field is required, or when the event defines the field.
- **Known contradiction.** `examples/full` and the reference CLI do not follow the literal text:
  - `application_id` has a base `dict` + `valueRequired`, and every event sets `value: web-app`/`mobile-app`.
  - `dimension_1` has a base `enum`, and `dashboard_view.yaml` sets `value: enterprise`.
  - A literal shallow merge yields dict+value or enum+value, which `field.schema.json` forbids, so any validator, including the `validate()` subset, rejects such a merged field. `validate.ts` never merges layers, so it cannot detect this and passes `examples/full`. The CLI also accepts the plan.
  - The docs' own pinned-value pattern (`docs/schema/opentp-yaml.md` "valueRequired": base `dict` + `valueRequired`, each event sets `value`) also works only with a narrowing merge.
  - Root cause: `d9d6be9` dropped the 2025-12 rule "an override `value`/`enum`/`dict` first removes the base `value`/`enum`/`dict`" from events.md; opentp-cli `mergeField` still implements it.
  - Resolving it is an owner decision: document the narrowing override in `semantics.md`, or change CLI + examples. Until then, explain narrowing as the reference behaviour and the "shallow merge" wording as a known spec bug. Never quietly "fix" only one side, and do not edit `examples/full` to satisfy the literal text.

### For implementers (reference CLI behaviour, opentp-cli)

- **`mergeField`** (`src/core/payload.ts`): an override `value` drops the base `enum`/`dict`, an override `enum` drops `value`/`dict`, and an override `dict` drops `value`/`enum`. `pii`, `x-opentp` and `x-opentp.checks` are merged by key, one level deep.
- **Conflict checks** (type change, weakening `required`, weakening `valueRequired`) run at every merge step:
  - global → `spec.targets.<id>.schema`: in `validateEvents` (`src/core/validator.ts`), once per run;
  - base → event: in `validatePayload` (`validator.ts`), per target and version;
  - `$ref` source → version: `mergeSchemaMaps` with issues (`payload.ts`), so a `$ref`-derived version cannot change a type or relax `required`.
- **Membership and subset checks** (`validateFieldExclusivity` in `src/rules/validation.ts`, plus the base-`dict` checks in `validatePayload`) compare the event layer with the merged base, before the event merge.
- **Gaps not to copy:** an event `dict` over a base `enum` or `dict` is not checked; an event `enum` that replaces a base `value` is not checked; selector-group members that are not in `all` are silently dropped.
- **De facto conformance cases:** opentp-cli `tests/data/coverage-valid` and `tests/data/coverage-invalid`, with expected errors in `src/core/fixtures.spec.ts` (partial `expect.objectContaining` assertions).
- **YAML parsers:** the CLI uses npm `yaml` 2.8.1 (YAML 1.2 core schema). PyYAML and SnakeYAML implement YAML 1.1: `yes`/`no`/`on`/`off` become booleans and unquoted dates become date objects (verified with PyYAML), so a validator built on them disagrees with the CLI on user files. Use a YAML 1.2 loader (candidates: ruamel.yaml, snakeyaml-engine) and test it on these scalars. The spec examples quote dates.

## `scripts/validate.ts`

`validateRepo(repoRoot)` runs these steps:
1. **Load schemas.** It loads every `schemas/*.json` (non-recursive), keyed by basename. A JSON parse error throws.
2. **Check `$ref` targets.** Every non-remote `$ref` to a `*.json` file must exist in `schemas/`. A guard throws if `.json` refs exist but none were checked.
3. **Validate examples.** It parses every `examples/**/*.yaml` (`.yml` is ignored) and picks a schema in `pickSchema`:
   - the basename `opentp.yaml` → the opentp schema;
   - keys `opentp`+`info`+`spec` → opentp;
   - keys `opentp`+`event` → event;
   - keys `opentp`+`dict` → dict;
   - anything else fails with "Cannot decide schema".
4. **Check Markdown.** It scans `README.md` and `docs/**/*.md` (not CONTRIBUTING.md or AGENTS.md) for blocks matching `` /```ya?ml\r?\n([\s\S]*?)\r?\n```/ ``:
   - Every block must parse.
   - Only blocks that `pickSchema` recognises as full files are schema-validated (today 7 of 44). Fragments are only parsed.
   - A fence with an info string after `yaml`, or with an indented closing fence, is not extracted correctly.

`main()` takes the parent of `scripts/` as the repo root (`path.resolve(import.meta.dir, "..")`), so the script can run from any cwd. `validateRepo(root)` throws ENOENT unless `README.md`, `schemas/`, `examples/` and `docs/` all exist (this also applies to test fixtures).

Output and exit codes: on success it prints the INFO and OK lines and exits 0. On failure it prints `FAILURES:` (at most 50 errors per file) and exits 1. A thrown structural error goes to stderr with exit 1.

**Supported JSON-Schema subset** (in `validate()`, not exported):
- `$ref`: local `#/...` and `file.json#/...`, resolved by basename. Remote refs are reported as errors. Sibling keywords are ignored.
- Combinators: `allOf`, `anyOf`, `oneOf` (exactly one), `not`.
- Values: `const` and `enum` (primitive `===` only); `type` (a single string; on a mismatch the remaining checks are skipped).
- Strings: `pattern`, `minLength`, `maxLength`.
- Objects: `required`, `properties`, `additionalProperties` (`false` or a schema), `minProperties`, `maxProperties`.
- Arrays: `items` (single schema), `minItems`, `maxItems`, `uniqueItems`.
- Numbers: `minimum`, `maximum`, numeric `exclusiveMinimum`/`exclusiveMaximum`, `multipleOf`.

**Silently ignored:**
- `format` (so `deprecatedAt: not-a-date` passes);
- type arrays, `patternProperties`, `propertyNames`, `dependencies`, `if/then/else`, `contains`, tuple `items`, `additionalItems`;
- deep-equality `const`/`enum`;
- `$schema` (never read).

Errors from `oneOf`/`anyOf` carry no branch detail. Example: `oneOf expected exactly 1 match, got 0`.

**YAML quirk:** Bun 1.3.6 `Bun.YAML.parse` reads unquoted `2026-01` as the number `2026`. `patchYamlForBun` quotes only whole lines of the form `opentp: YYYY-MM` (an optional comment is allowed). Any other unquoted YYYY-MM-like scalar (e.g. `current: 2026-02`, a `2026-02:` version key, dict values, alias values) must be quoted: Bun reads it as the number `2026`, while the reference CLI's npm `yaml` package (YAML 1.2 core) keeps it as a string, so the two parsers disagree. Separately, quote decimal-looking versions such as `1.0`, which are numbers in **both** parsers (fatal for `info.version`, `current` and alias values). Full dates like `2025-01-01` stay strings in both.

**Proving a rejection** (there are no negative tests). With cwd = repo root:

```bash
T=$(mktemp -d) && cp -R schemas scripts examples docs README.md "$T"/
# put the bad YAML into $T/examples/... or into a doc block, then:
bun "$T/scripts/validate.ts"   # expect exit 1 and the specific error
```

For example, adding `deprecated: true` to `user_id` in the copied `examples/full/opentp.yaml` gives `root.spec.events.payload.schema.user_id: additional property not allowed: "deprecated"`.

**Checking doc fragments (manual; not automated yet).** In a scratch copy, export `validate()` and call `validate(node, { $ref: "<file>#<pointer>" }, "root", { schemaName: "opentp.schema.json" }, schemas)`, where `schemas` maps basename → parsed JSON. These pointers cover every current fragment:
- `opentp.schema.json#/definitions/{taxonomyField,targetConfig,eventKeyConstraints,xOpentpEvents,piiConfig}`
- `opentp.schema.json#/properties/spec/properties/{paths,events/properties/payload}`
- `field.schema.json` (one payload field)
- `event.schema.json#/properties/event/properties/{payload,lifecycle,aliases,ignore}`

To automate it, each block needs a hint that maps a node to a pointer. A fence info string (```` ```yaml x ````) breaks the current fence regex. A first-line `# ...` comment works with it, but shows on GitHub and opentp.dev. An HTML comment above the fence is invisible in both places, but needs a regex change. Skip comment-only and `opentp:`-only blocks, give deliberately wrong examples (the events.md "Don't" block) an explicit opt-out, run the check inside `validateRepo` so CI enforces it, and add a negative test.

## Schema publishing (cross-repo)

- There is no build or package. jsDelivr serves files straight from git tags: `https://cdn.jsdelivr.net/gh/opentrackplan/opentp-spec@<tag>/schemas/<file>`.
- `opentp.dev/schemas/...` maps to jsDelivr through **`opentp-website/public/_redirects`** (302 rules; the website repo is private). Today all three rules (`/schemas/2025-12/*`, `/schemas/latest/*`, catch-all `/schemas/*`) point at `@2025-12`. There is **no `2026-01` rule**, and the `2025-06` rule was dropped in opentp-website `56e40fd`.
- **Effect (verified 2026-10-02):** `https://opentp.dev/schemas/2026-01/*` returns 302 to `@2025-12/schemas/2026-01/...` and then 404. `/schemas/latest/*` serves the **2025-12** schemas, which reject every 2026-01 `opentp.yaml` (they require `paths.events.pattern`). jsDelivr `@2026-01` works. The fix belongs in `_redirects`, never in `$id`.
- Relative `$ref`s resolve against `$id`. Every version that appears in any `$id` therefore needs its own redirect rule, even for files fetched via `latest/`.
- **In-place edits to a published version are never served.** `opentp.dev/schemas/<ver>/*` points at jsDelivr `@<ver>`, an immutable tag. A schema change committed after the tag reaches users only with the next `YYYY-MM` tag. Until then, `main` (and any website docs synced from it) is ahead of the published schemas, and IDEs using the published schemas reject the new keyword. For a new keyword:
  1. Ask the owner whether it waits for the next version or is an explicit exception.
  2. Record the decision in `CHANGELOG.md` (create it if missing) under the target version, and in the commit body.
  3. Do not resync website docs from `main` until the tag exists.
- The website copies **`docs/` only**:
  - `scripts/sync-docs.sh` sparse-clones the default branch, not a tag; `sync-docs-local.sh` copies from `../opentp-spec/docs`.
  - Both add frontmatter, and the result is committed under `src/content/docs/docs/spec/`.
  - Whatever is on `main` reaches the site at the next manual sync.
- The CLI prints `https://opentp.dev/schemas/<specVersion>` (opentp-cli `src/meta.ts` `SPEC_SCHEMAS_URL`), and the CLI docs use `/schemas/2026-01/` URLs. This repo's docs use `/schemas/latest/` URLs.

## Recipes

### Add or change a Field keyword
1. **Check for an existing shape.** A new concept should reuse one that already exists. For example, a Field-level deprecation should reuse `{reason, date}` (see "Event file"); a bare boolean needs the owner's explicit OK. Also decide how it merges across layers and say so in `docs/semantics.md` (by default an event can set `false` over a base `true`).
2. **`schemas/field.schema.json`.**
   - Add the keyword to the top-level `properties`. This is mandatory: with `additionalProperties: false`, properties declared only inside a branch do not whitelist the key.
   - If it is type-specific, add `{ "required": ["<kw>"] }` to the `not.anyOf` list of every non-applicable typed branch in `oneOf`. If it is a constraint, also add it to the untyped branch.
   - If its value type depends on `type` (like `value`/`example`), add a typed override in each branch's `properties`.
3. **Array items.** If it applies to them, update `definitions.arrayItems` and its `oneOf`.
4. **Mirrors in `schemas/opentp.schema.json`**, where applicable:
   - `definitions.taxonomyField` and its type `oneOf` inside `allOf`;
   - `definitions.piiMetaField` and its `oneOf`;
   - `definitions.piiReservedFieldConfig` (string-only);
   - `definitions.eventKeyConstraints`.
5. **Known duplicates.** The `x-opentp` shape lives in both `field.schema.json#/definitions/xOpentp` and `opentp.schema.json#/definitions/xOpentpField`. The `format` enum has 6 copies: 4 in opentp.schema.json and 2 in field.schema.json.
6. **Validator support.** Use only keywords from the validator subset, or extend `validate()` and add a test.
7. **Docs:**
   - `docs/schema/events.md` (the "Payload field definition" table and constraints list);
   - `docs/schema/opentp-yaml.md` (the taxonomy constraint list and payload notes);
   - `docs/semantics.md` if merge behaviour is special;
   - README if it is a headline feature.
8. **Examples.** Use the keyword in `examples/full` (or `simple` if it is core) so the validator exercises it. Prove that a misplaced use is rejected (see "Proving a rejection").
9. **Version decision.** Follow "In-place edits to a published version are never served" (Schema publishing). The owner decides; the decision goes into `CHANGELOG.md`.
10. **Checks and downstream.** Run the checks. The CLI silently accepts unknown Field keys, so list CLI support (opentp-cli `src/types/index.ts`, `src/core/validator.ts`) as a follow-up.

### Add or modify a doc page
1. Put the page under `docs/` and start it with exactly one `# Title`. The website sync takes the Starlight title from the first H1, unless the page is in its explicit `add_frontmatter` list.
2. Link the page from `docs/index.md` and from the README "Documentation" list (and from `docs/schema/index.md` for schema pages). Note that README does not link `semantics.md` today.
3. YAML fences:
   - Use a plain ```` ```yaml ```` fence.
   - Full-file blocks are schema-validated; use them for anything that claims to be a complete file.
   - Check fragments against the right definition (see "Checking doc fragments"): taxonomy fields need `title`+`type`, and payload fields need `type` or `value`.
4. Keep relative `.md` links (they work on GitHub). The website must also add the page to the explicit sidebar in `opentp-website/astro.config.mjs`.

### Cut a new spec version `YYYY-MM`
In this repo:
1. Set `$id` in all 5 schemas to `https://opentp.dev/schemas/YYYY-MM/...`, and update the `examples` in `version.schema.json`.
2. Replace `opentp: <old>` in all 14 example YAMLs and every Markdown block, including fragments. Find them with `git grep -n "<old>" -- . ':!AGENTS.md' ':!scripts'`.
3. Update the README "Specification Version" section, "Format Version" in `docs/index.md`, and the `opentp` row example in `docs/schema/opentp-yaml.md`.
4. Write migration notes (old key → new key) in `CHANGELOG.md` (create it if missing).
5. Update this file: the Status table (current version, Tags row), the `$id` example under "Format model", and the tag list in the "Never move... a published tag" rule. In the local workspace, also update the "Spec version" line in `../AGENTS.md`.
6. Run the checks. Commit, then create and push an annotated tag, only when the user asks: `git tag -a YYYY-MM -m "Spec YYYY-MM" && git push origin YYYY-MM`. Never re-point it afterwards.

Cross-repo order (details: `../opentp-website/AGENTS.md` "Publish a new spec version" and `../opentp-cli/AGENTS.md` "Bump the spec version"):
1. Spec tag pushed (step 6 above).
2. jsDelivr serves it: `curl -s -o /dev/null -w '%{http_code}\n' https://cdn.jsdelivr.net/gh/opentrackplan/opentp-spec@YYYY-MM/schemas/opentp.schema.json` prints `200`.
3. Website: add `/schemas/YYYY-MM/* https://cdn.jsdelivr.net/gh/opentrackplan/opentp-spec@YYYY-MM/schemas/:splat 302`, plus the missing `2026-01` and `2025-06` rules, above `latest` and the catch-all (the top-most match wins). This is safe to deploy right away.
4. CLI release with the new `specVersion` (the CLI accepts exactly one version).
5. One website push that repoints `latest/*` and the catch-all to the new tag, resyncs the docs, and updates the landing snippet in `src/pages/index.astro` (it still shows `2025-12`).
6. Smoke-test every `$id`, e.g. `curl -sSL https://opentp.dev/schemas/YYYY-MM/opentp.schema.json | grep -F '"$id"'`.

Pushing opentp-website `main` is the production deploy (Cloudflare Pages Git integration). `astro dev` and `astro preview` ignore `_redirects`, so verify on a Cloudflare preview deploy or after the deploy. If `latest` moves before step 4, users who follow the `latest` modelines in these docs are pushed to a format that the released CLI still rejects.

### Downstream invariants
- **opentp-cli** (public): it never loads this repo's schemas, so every schema rule is reimplemented by hand. It accepts exactly one `specVersion` and rejects any other `opentp` value. Steps: `../opentp-cli/AGENTS.md` ("Bump the spec version", "Add or change a validation check").
- **opentp-website** (private): `_redirects` needs one rule per version that appears in any `$id`; `src/content/docs/docs/spec/` holds synced copies of `docs/`. Steps: `../opentp-website/AGENTS.md` ("Publish a new spec version", "Resync docs after a spec or CLI docs change", "Add a docs page").
- **opentp-sdk** (public `@opentp/sdk` 0.1.0, TypeScript runtime SDK; not checked out locally): no direct dependency on this repo is known. Its README expects a typed tracker generated by opentp-cli, which the CLI cannot produce yet.

## Known issues & traps (verified 2026-10-02)

Covered in their own sections: broken published schema URLs ("Schema publishing"), the merge contradiction ("Normative semantics"), and the YAML parser quirk (`scripts/validate.ts`).

- **Field overrides need `type` or `value`.** An event-layer override such as `{required: true}` or `{pii: {...}}` alone fails `field.schema.json` (anyOf type/value), although the CLI accepts it. Only `value` can be overridden without restating `type`.
- **Most doc YAML blocks are never schema-checked** (37 of 44). These fragments in `docs/schema/dictionaries.md` are invalid today:
  - "In Taxonomy": `area` has no `title`;
  - "Dictionary vs Enum": `dict`/`enum` fields have no `type`;
  - "In Event Files": `payload:` sits at the file root instead of under `event:`.
- **No negative tests.** A validator that returned no errors would still pass CI.
- **`version.schema.json` does not pin the version**, so 2026-01 schemas accept `opentp: 2025-12`. The CLI requires an exact match (`config.ts`, plus the dict and event checks).
- **`examples/extensions` fails the reference CLI** with `taxonomy.action: Unknown check: mytool.not-empty` (exit 1). `docs/schema/index.md` says extensions "can be ignored", and the spec does not define namespaced check ids. Keep the example; this needs a spec/CLI decision.
- **The CLI accepts unknown Field keys.** Adding `deprecated: true` to `examples/full` still prints `All events are valid count=5`, so a CLI run proves nothing about a new keyword.
- **Non-canonical meta-schema URI.** All schemas declare `"$schema": "https://json-schema.org/draft-07/schema#"`, and Ajv 8 with defaults fails with `no schema with key or ref`. The canonical id is `http://json-schema.org/draft-07/schema#`. Changing it is a schema change, so coordinate it.
- **Website rendering.** Relative `.md` links from `docs/` 404 on opentp.dev (e.g. `/docs/spec/schema/opentp-yaml.md`), and `semantics` is missing from the website sidebar. Fix these in opentp-website, not by rewriting links here.
- **Markdown glitches:** in `docs/semantics.md` the `$ref` forms are written as `"$ref: \"<versionKey>\""` inside code spans, so backslashes render. `docs/schema/events.md` shows `payload::\<field>`.
- **Undefined in the spec:** the meaning of uncovered targets, of a leading `/` in `paths.*.root` (the CLI strips it and joins with the project root), and of `x-opentp.role`. The YAML dialect is unspecified. `examples/**/*.yml` files are never validated.

## Definition of done

- [ ] Schemas, docs (`docs/`, including `semantics.md` when behaviour changes), examples and `README.md` describe the same format; terminology matches everywhere:
  - `template` (paths/composite/keygen) vs `pattern` (regex);
  - `x-opentp.checks`;
  - `pii.kind`/`pii.masker`;
  - `current`, aliases, `$ref`, `<payloadKey>::<versionKey>`.
- [ ] Every copy of a duplicated definition is updated (`xOpentp`/`xOpentpField`, the `format` enum, taxonomy and pii mirrors).
- [ ] New schema keywords are within the validator subset, or `validate.ts` is extended with a test. A rejection of misuse was proven on a scratch copy.
- [ ] New or changed doc YAML fragments are checked against their schema pointer. Full-file blocks parse and validate.
- [ ] `bun scripts/validate.ts` exits 0 and `bun test scripts/validate.test.ts` passes (Bun 1.3.6).
- [ ] Optional: the reference CLI still validates `examples/simple` and `examples/full`, and the `extensions` result is unchanged or improved. This catches semantic regressions only (the CLI accepts unknown Field keys; see Known issues).
- [ ] Any change to a published version follows "In-place edits to a published version are never served": the owner decided, and `CHANGELOG.md` records it. No published tag is moved.
- [ ] Downstream follow-ups are listed for opentp-cli and opentp-website ("Downstream invariants").
- [ ] Nothing was committed, tagged or pushed without the user asking. The commit message is in English.
