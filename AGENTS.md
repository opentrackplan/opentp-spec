# opentp-spec: Agent Guide

This repo is the source of truth for the **OpenTrackPlan file format**: JSON Schemas (`schemas/`), normative and reference docs (`docs/`), example tracking plans (`examples/`), the changelog with migration notes (`CHANGELOG.md`) and a consistency checker (`scripts/validate.ts`). It contains no runtime code; its only package is the npm `yaml` parser that the checker uses. The reference implementation lives in `opentrackplan/opentp-cli`.

## Rules

- **English only** in code, comments, docs, examples and commit messages.
- **Do not commit, tag or push unless the user asks.** A pushed tag is permanent: jsDelivr caches it as immutable, and the next rule forbids moving it. Run every check before proposing `git tag`.
- **Never move, delete or re-push a published tag** (`2025-06`, `2025-12`, `2026-01`, and `2026-09` once it is pushed). jsDelivr serves tagged files with `cache-control: ... max-age=31536000, immutable`, so a moved tag never propagates and clients end up with different files.
- **Published versions are immutable.** Every format change goes into the next `YYYY-MM` version and its `CHANGELOG.md` entry. The in-place amendment of `2026-01` (`27b1a4c`, 2026-06-20) is recorded as a one-time exception; do not repeat it.
- **Change things together.** A format change touches `schemas/`, `docs/` (normative rules in `docs/semantics.md`), `examples/`, `README.md` and `CHANGELOG.md` in the same change. Docs snippets must match the schemas, and examples must match both the schemas and the validator-only rules.
- **Only use JSON-Schema keywords that `scripts/validate.ts` implements** (see the subset below). The checker throws at load on any other keyword, on a keyword value of the wrong type (for example `minItems: "1"` or a draft-04 boolean `exclusiveMinimum`), on `$id`/`$schema` below a file's root, on a validation keyword next to `$ref`, and on a `$ref` that does not resolve or whose file part contains `/`. Extend the validator and add a test in the same change if you need more.
- **Never put a validation keyword next to `$ref`**: draft-07 engines ignore `$ref` siblings. Wrap the constraint in `allOf` (as `catalogField` and `eventField` do). `description`, `title` and `$comment` next to `$ref` are fine.
- **Edit docs here, never the website copies.** `opentp-website/src/content/docs/docs/spec/` is generated by that repo's sync scripts.
- Every `examples/**/*.yaml` and `*.yml` must be a complete opentp.yaml, event or dictionary file. Tool files (`opentp.cli.yaml`, `opentp.cli.yml`) are skipped; keep them out of `examples/`.
- Every YAML block in `README.md` and `docs/` must be valid 2026-09, or be directly preceded by `<!-- invalid: <expected error substring> -->`.
- Prefer the minimal form in docs and examples (implicit payload, unversioned, event fields without `type`). Show the expanded form only where it is the topic.

## Format model (2026-09, compact)

Common to all schemas:
- Draft-07 with the canonical `"$schema": "http://json-schema.org/draft-07/schema#"` and `$id: https://opentp.dev/schemas/2026-09/<name>.schema.json`. Cross-file `$ref`s are relative file names (`version.schema.json`, `field.schema.json#/definitions/...`), so they resolve against `$id`.
- Every file has a top-level `opentp: 2026-09` (`version.schema.json` pins it with `const`).
- Fixed-shape objects are closed: `additionalProperties: false`, `patternProperties: {"^x-": {}}` and `"x-opentp": {"not": {}, "description": "Removed in 2026-09; see CHANGELOG.md"}`. Maps keyed by user names (targets, checks, taxonomy, fragments, field maps, the payload map form, versioned payloads) never treat `x-` specially. A `$schema:` key inside YAML is an error; use the comment `# yaml-language-server: $schema=...` instead.

### opentp.yaml

```text
opentp*: "2026-09"
info*:    { title*, version* (string), description, contact: string[], x-* }
spec*:
  paths*:   { events*: { root*, template*, x-* }, dictionaries: { root*, x-* }, x-* }
  targets:  { all: TargetConfig, <targetId>: TargetConfig }     # keys: "all" or ids from payload.targets.all (validator rule)
  checks:   { <checkId>: PortableCheck }                         # ids match ^[A-Za-z][A-Za-z0-9_.-]*$
  events*:
    key:       { minLength, maxLength, pattern, format, x-* }   # constraints only
    taxonomy*: { <fieldId>: TaxonomyField }                       # may be {}
    payload*:  { targets*: { all*: [targetId, ...] (minItems 1, unique, non-empty), <group>: [targetId, ...] },
                 schema: { <field>: CatalogField },               # the catalog; optional, default {}
                 x-* }
    pii:       { kind: PiiReserved, masker: PiiReserved, schema: { <metaKey>: PiiMetaField }, x-* }
    x-*
  x-*
x-*
TargetConfig  = { title, description, schema: { <field>: Field }, x-* }
PortableCheck = { title, description, <portable keywords> (at least one), x-* }
```

- **Portable keywords:** `minLength maxLength pattern format minimum maximum exclusiveMinimum exclusiveMaximum multipleOf`.
- **Grammars** for the path template and composite taxonomy fields: `docs/schema/opentp-yaml.md`. Key generation is tool configuration (the reference CLI reads it from `opentp.cli.yaml`); the spec defines no keygen grammar.
- **TaxonomyField:** requires `title` and `type` (`string|number|integer|boolean`). Optional: `description`, `required`, `enum` (minItems 1) | `dict`, constraints by type, `checks`, `x-*`. A composite field uses `template` + `fragments` (both or neither, string only); fragment ids become taxonomy keys. No `value`, `example`, `name` or array type.

### Event file

```text
opentp*: "2026-09"
event*:
  key*:      string (minLength 1), opaque, unique per plan
  lifecycle: { status: active|deprecated|draft, deprecatedAt (date), deprecatedReason, replacedBy: key, x-* }
  taxonomy*: object                      # required even if {}; validated against spec.events.taxonomy
  aliases:   [ { key*, deprecated: { reason, date, x-* }, x-* } ]
  ignore:    [ { path*, reason, x-* } ]  # path grammar: docs/semantics.md "Ignore"
  payload*:  Target | { <selectorOrTargetId>: Target }      # minProperties 1
  x-*
x-*
Target          = PayloadVersion | VersionedTarget
PayloadVersion  = { schema*: { <field>: EventField }, meta: { changes: string|string[], deprecated: { reason*, date, x-* }, x-* }, $ref: string, x-* }
VersionedTarget = { current*: string, <versionKey>: PayloadVersion, <aliasKey>: "<key>" }   # `schema` key forbidden
```

- Payload forms: implicit unversioned (`payload.schema`), implicit versioned (`payload.current`), map form (`payload.<key>`, each value one of the two). The normative selector → target algorithm is in `docs/semantics.md` ("Payload resolution"); an uncovered target means the event is not sent there (valid).
- Deprecation has three shapes: `lifecycle` (`status`, `deprecatedAt`, `deprecatedReason`, `replacedBy`), `aliases[].deprecated` (`{reason?, date?}`) and `meta.deprecated` (`{reason*, date?}`). Only `meta.deprecated` has an effect (versions exempt from policy). Fields have no deprecation keyword.
- Quote version keys and alias values that look like numbers (`"1.0.0"` is a string anyway; `"1.0"` is not).

### Field (`field.schema.json`)

| Use | Where | Schema |
|---|---|---|
| CatalogField | `spec.events.payload.schema.<f>` | `#/definitions/catalogField`: `type` required; `items` required for arrays |
| Common field (BaseField) | `spec.targets.<id>.schema.<f>` | the root schema (validators require a `type` after merging catalog → `all` → `<id>`) |
| EventField | payload version `schema.<f>` | `#/definitions/eventField`: `policy` forbidden; `type` optional (inherited) |

- **Keywords:** `name` (code-facing name), `title`, `description`, `type`, `enum` (non-empty, scalars), `dict`, `value`, `required`, `policy` (`specified|restricted|fixed`), `example`; string constraints `minLength maxLength pattern format`; number constraints `minimum maximum exclusiveMinimum exclusiveMaximum multipleOf`; array `items minItems maxItems uniqueItems`; `pii` (`kind`, `masker` reserved strings; extra keys allowed); `checks` (`#/definitions/checks`); `x-*`.
- **Within one definition** (root `allOf`, each with a `description` that the checker prints): `enum`, `dict` and `value` are pairwise exclusive; `required: false` next to `value` is invalid; `required: false` next to `policy: restricted|fixed` is invalid.
- **`oneOf` branches:**

  | Branch | Allowed | Typing of `enum`/`value`/`example` |
  |---|---|---|
  | untyped (no `type`) | everything (validators check against the inherited type) | scalars / scalar arrays |
  | `string` | `minLength maxLength pattern format` | strings |
  | `number` / `integer` | `minimum maximum exclusiveMinimum exclusiveMaximum multipleOf` | numbers / integers |
  | `boolean` | no constraints | booleans |
  | `array` | `items minItems maxItems uniqueItems`; top-level `enum`/`dict` forbidden (use `items.enum`/`items.dict`) | `value`/`example` are scalar arrays |

- **`arrayItems`:** optional scalar `type` (required on the effective field), `enum` (minItems 1) | `dict`, scalar constraints, `checks`, `x-*`. `object` is intentionally not a type.
- **Defined once** in `field.schema.json#/definitions`: `format` (`date date-time email uuid uri ipv4 ipv6`), `scalar` (string | number | boolean) and `checks` (`patternProperties {"^[A-Za-z][A-Za-z0-9_.-]*$": {}}`, `additionalProperties: false`). `opentp.schema.json` references them; never copy them.

### Dictionaries

`{ opentp, dict: { type*: string|number|integer|boolean, values*: [...] (minItems 1, unique, typed), x-* }, x-* }`. Values carry no metadata. A reference `<path>` resolves to `<root>/<path>.yaml` or `.yml` (both: error).

## Normative semantics (`docs/semantics.md`)

The schemas cover each file's shape; `docs/semantics.md` defines the rest. In short:

- **Layers** per `(event, target, version)`: catalog → `spec.targets.all` → `spec.targets.<T>` → event layer (after `$ref`). The field set is the common fields of `T` plus the fields the event lists; a catalog field the event does not list is not part of it.
- **Field merge (narrowing):** a later `value` must equal an earlier `value` or belong to the earlier `enum`/`dict`; a later `enum`/`dict` must be a subset and cannot replace a fixed `value`; `required: true` cannot be weakened; `policy` only on base layers, raised but never lowered; `checks`/`pii` merge by key; `x-*` keys replace whole; other keywords: later wins. Between `$ref` versions values change freely (only a `type` change and `required: true` → `false` are errors).
- **Presence:** `required: true` in any layer, a `value`, or a non-exempt `policy: restricted|fixed` means always present. `meta.deprecated` versions are exempt from policy.
- **Closed vocabulary** per target, **type inheritance** (event fields never need `type`). Keywords that depend on the type are checked against the effective type in every layer: no top-level `enum`/`dict` on arrays (so `policy: restricted` on an array field needs `value`), string constraints only on strings, number constraints only on numbers, array keywords only on arrays.
- **YAML:** validators report a plain `<<` mapping key (merge key) as an error that cannot be ignored.
- **Event predicate:** AND over the effective fields (`value` → `=`, `enum`/`dict` → `IN`, plus `OR IS ABSENT` when optional; free fields unrestricted); OR over versions. Overlap between events is reported by tools, not an error.
- **Checks:** `spec.checks` ids are portable (params `true`/`false`); other ids are tool-defined, and unknown ones may be ignored with a warning.
- **Ignore:** `key`, `opentp`, `taxonomy.<name>`, `payload::<f>`, `payload.<f>[...]`, `payload.<...>.schema.<f>[...]`; a fixed list of problems is never ignorable.
- **Validator-only rules** are listed at the end of `docs/semantics.md`. Keep that list in sync when a rule moves into or out of the schemas.

### For implementers (reference CLI)

- opentp-cli 0.10.0 reads exactly spec `2026-09` (`package.json` `specVersion`) and upgrades 2026-01 plans with `opentp migrate`. It never loads these schemas, so every rule is reimplemented by hand (`src/core/payload.ts` for the merges, `src/core/validator.ts`, `src/core/overlap.ts`); see `../opentp-cli/AGENTS.md`. A CLI pass therefore does not prove schema validity: run `validate.ts` too.
- Tool settings (keygen, check bindings and plugins, tracker binding, generators, MCP) live in `opentp.cli.yaml`, whose JSON Schema belongs to opentp-cli (`https://opentp.dev/schemas/cli/opentp.cli.schema.json`), not to this repo.
- **De facto conformance cases:** opentp-cli `tests/data/coverage-valid` and `tests/data/coverage-invalid`, with expected errors in `src/core/fixtures.spec.ts`.
- **YAML parsers:** the CLI and `validate.ts` use npm `yaml` 2.8.4 (YAML 1.2 core schema). PyYAML and SnakeYAML implement YAML 1.1: `yes`/`no`/`on`/`off` become booleans and unquoted dates become date objects, so a validator built on them disagrees with the spec on user files. Use a YAML 1.2 loader (candidates: ruamel.yaml, snakeyaml-engine) and test it on these scalars and on duplicate keys and `<<`.

## `scripts/validate.ts`

`validateRepo(repoRoot)` runs these steps:
1. **Load and check schemas** (`loadSchemas`, `checkSchemas`). It loads every `schemas/*.json` (non-recursive), keyed by basename, and throws with the full list of problems when a schema:
   - does not declare the canonical draft-07 `$schema`, or has an `$id` other than `https://opentp.dev/schemas/<version const>/<file>` (so a partial version bump fails);
   - uses a keyword outside the subset below, a `type` that is not one string, tuple `items`, or a `format` the checker does not implement;
   - gives a keyword a value of the wrong type (draft-07 meta-schema): non-negative integers for `minLength`/`maxLength`/`minItems`/`maxItems`/`minProperties`/`maxProperties`, numbers for `minimum`/`maximum`/`exclusiveMinimum`/`exclusiveMaximum`, a number > 0 for `multipleOf`, a boolean for `uniqueItems`, unique strings for `required`, arrays for `enum`/`examples`, strings for the annotations, objects for `properties`/`patternProperties`/`definitions` (`validate()` would otherwise skip the keyword silently);
   - has `$id` or `$schema` below the root of the file (a nested `$id` changes how other engines resolve `$ref`s);
   - has a keyword other than `description`/`title`/`$comment` next to `$ref`, or a `$ref` that does not resolve (remote refs are not supported) or whose file part contains `/` (it must be a file name in `schemas/`, so Ajv and IDEs resolve it to the same file);
   - has a `pattern` or `patternProperties` key that does not compile with the `u` flag.
2. **Validate examples.** It parses every `examples/**/*.{yaml,yml}` except `opentp.cli.yaml`/`opentp.cli.yml` and picks a schema in `pickSchema`: basename `opentp.yaml`/`opentp.yml` → opentp; keys `opentp`+`info`+`spec` → opentp; `opentp`+`event` → event; `opentp`+`dict` → dict; anything else fails with "Cannot decide schema".
3. **Check Markdown.** It scans `README.md` and `docs/**/*.md` (not `CHANGELOG.md`, `CONTRIBUTING.md` or `AGENTS.md`) for blocks matching `` /```ya?ml\r?\n([\s\S]*?)\r?\n```/ ``:
   - every block must parse;
   - blocks that `pickSchema` recognises as full files must match their schema;
   - a block directly preceded by `<!-- invalid: <text> -->` (only whitespace between) must fail with an error (or parse error) that contains `<text>` if it is a full file; a marked fragment is skipped;
   - fragments are only parsed (check them by hand, below). A fence with an info string after `yaml`, or with an indented closing fence, is not extracted correctly.

`main()` takes the parent of `scripts/` as the repo root, so the script can run from any cwd. `validateRepo(root)` needs `README.md`, `schemas/`, `examples/` and `docs/` (the tests copy exactly these).

Output and exit codes: on success it prints the INFO and OK lines and exits 0. On failure it prints `FAILURES:` (at most 50 errors per file) and exits 1. A schema problem found at load goes to stderr with exit 1.

**YAML:** `parseYaml` is `parse()` from npm `yaml` with defaults: YAML 1.2 core schema (`opentp: 2026-09` is a string without quotes), duplicate keys throw, `<<` is an ordinary key (the closed schemas then reject it on fixed-shape objects; a `<<` name in a map keyed by user names is a validator-only error that this checker does not report).

**Supported JSON-Schema subset** (`validate()`):
- `$ref`: local `#/...` and `file.json#/...`; the file part is a file name in `schemas/` (no `/`).
- Booleans as schemas (`true` passes, `false` fails).
- Combinators: `allOf`, `anyOf`, `oneOf` (exactly one), `not`.
- Values: `const` and `enum` (deep equality); `type` (one string; on a mismatch the remaining checks are skipped).
- Strings: `pattern` (`u` flag, not anchored), `minLength`, `maxLength` (code points), `format` (`date date-time email uuid uri ipv4 ipv6`, as defined in `docs/semantics.md`).
- Objects: `required`, `properties`, `patternProperties`, `additionalProperties` (`false`, `true` or a schema; applies to keys matched by neither `properties` nor `patternProperties`), `minProperties`, `maxProperties`.
- Arrays: `items` (one schema), `minItems`, `maxItems`, `uniqueItems` (deep).
- Numbers: `minimum`, `maximum`, numeric `exclusiveMinimum`/`exclusiveMaximum`, `multipleOf`.
- Annotations: `$schema` and `$id` (root only), `$comment`, `title`, `description`, `examples`, `definitions`.

**Error messages:** `{ "not": {} }` prints `not allowed (<description>)`; any other failing `not` prints the `description` of its schema (so give rule-like `not`s a description); a failing `anyOf` appends its description; a `oneOf` with no match also prints the errors of the branch with the fewest errors (so errors inside event payloads keep their paths).

**Proving a rejection:** add a negative test to `scripts/validate.test.ts`. The helpers copy the repo to a temporary directory (`copyRepo`), edit a file with `edit` (which fails if the text to replace is missing) and assert on the error text.

**Checking doc fragments (manual).** From a scratch file outside the repo:

```ts
import { loadSchemas, parseYaml, validateNode } from "<repo>/scripts/validate.ts";
const schemas = await loadSchemas("<repo>/schemas");
console.log(validateNode(parseYaml(fragmentText), "field.schema.json#/definitions/eventField", schemas));
```

These pointers cover every current fragment:
- `opentp.schema.json#/properties/spec/properties/{paths,targets,checks}` and `.../properties/events/properties/{taxonomy,payload}`; the catalog map is `.../payload/properties/schema`;
- `opentp.schema.json#/definitions/{taxonomyField,eventKeyConstraints,piiConfig,portableCheck}`; a map of common fields is `#/definitions/targetConfig/properties/schema`;
- `field.schema.json` (a common field), `field.schema.json#/definitions/{catalogField,eventField}`;
- `event.schema.json#/properties/event/properties/{payload,lifecycle,taxonomy,aliases,ignore}`; a map of event fields is `#/definitions/payloadVersion/properties/schema`.

As of 2026-10-03 all 54 blocks check clean (7 full files, 47 fragments). Two are marked invalid on purpose: the `required: false` + `value` block in `docs/semantics.md` and the overlapping payload keys in `docs/schema/events.md` (a validator-only rule, so it is schema-valid).

## CI

`.github/workflows/validate.yml` runs on push or PR to `main`/`master`, on `workflow_dispatch`, and as a reusable workflow (`workflow_call`) from `release.yml`:
- ubuntu-latest, `actions/checkout@v4`, `oven-sh/setup-bun@v2` with `bun-version: '1.4.2'`;
- `bun install --frozen-lockfile`, `bun scripts/validate.ts`, `bun test scripts/validate.test.ts`.

CI does not run a TypeScript type-check, a real JSON-Schema engine (Ajv), a link check, the reference CLI on the examples, or a schema-URL smoke test.

- `CHANGELOG.md` has one section per version: `## [YYYY-MM] - <tag date>` with "Breaking", "Relaxed", "Added", "Removed" and a "Migration from <previous version>" table (old → new). Collect changes for the next version under `## [Unreleased]` and rename it to `## [YYYY-MM] - <date>` in the commit that gets the tag.
- `.github/workflows/release.yml` runs on a pushed tag matching `[0-9][0-9][0-9][0-9]-[0-9][0-9]`:
  1. `check-tag`: fetches the tag object, fails unless `git cat-file -t "$TAG"` prints `tag` (annotated), and fails unless `schemas/version.schema.json` has `"const": "$TAG"`;
  2. `verify`: `validate.yml`;
  3. `release` (`contents: write`): extracts the `## [$TAG]` section of `CHANGELOG.md` (fails if missing or empty) and runs `gh release create "$TAG" --verify-tag --title "OpenTrackPlan $TAG" --notes-file <section>` with `GH_TOKEN: ${{ github.token }}`.
- A failed release run never justifies moving the tag. Fix the cause, then re-run the workflow, or create the release by hand from the same notes.

## Schema publishing (cross-repo)

- There is no build or package. jsDelivr serves files straight from git tags: `https://cdn.jsdelivr.net/gh/opentrackplan/opentp-spec@<tag>/schemas/<file>`.
- `opentp.dev/schemas/...` maps to jsDelivr through `opentp-website/public/_redirects` (302 rules; the website repo is private). As of 2026-10-03 it has static rules for `/schemas`, `/schemas/latest` and `/schemas/<version>`, dynamic `/schemas/<version>/*` rules for `2026-01`, `2025-12` and `2025-06`, and `/schemas/latest/*` plus the catch-all `/schemas/*` on `@2026-01`. **There is no `2026-09` rule yet**; the website adds it after this tag exists, and repoints `latest` only after the CLI release that reads 2026-09.
- Relative `$ref`s resolve against `$id`. Every version that appears in any `$id` therefore needs its own redirect rule, even for files fetched via `latest/`.
- **Content after a tag is never served.** `opentp.dev/schemas/<ver>/*` points at jsDelivr `@<ver>`, an immutable tag. Until the next tag, `main` (and any website docs synced from it) is ahead of the published schemas. Do not resync website docs from `main` until the tag exists.
- The website copies **`docs/` only**: `scripts/sync-docs.sh` sparse-clones the default branch, `sync-docs-local.sh` copies `../opentp-spec/docs`. Both add frontmatter and rewrite relative `./x.md#a` and `../x.md#a` links to Starlight routes (a link without `./` or `../` is not rewritten). Links outside `docs/` (for example `CHANGELOG.md`) must be absolute GitHub URLs.
- The CLI prints `https://opentp.dev/schemas/<specVersion>` (opentp-cli `src/meta.ts` `SPEC_SCHEMAS_URL`). This repo's docs use `/schemas/latest/` modelines.

## Recipes

### Add or change a Field keyword
1. **Check for an existing shape.** A new concept should reuse one that already exists (for example a field-level deprecation should reuse `{reason, date}`). Decide how it merges across layers and between `$ref` versions, and add it to the field merge table in `docs/semantics.md`.
2. **`schemas/field.schema.json`.**
   - Add the keyword to the top-level `properties`. This is mandatory: with `additionalProperties: false`, properties declared only inside a branch do not whitelist the key.
   - If it is type-specific, add `{ "required": ["<kw>"] }` to the `not.anyOf` list of every non-applicable typed branch in `oneOf`. The untyped branch accepts everything.
   - If its value type depends on `type` (like `value`/`example`), add a typed override in each branch's `properties`.
   - If it is not allowed in events or in the catalog, encode it in `eventField` or `catalogField` (inside `allOf`, never next to `$ref`).
3. **Array items.** If it applies to them, update `definitions.arrayItems` and its `oneOf`.
4. **Mirrors in `schemas/opentp.schema.json`**, where applicable: `taxonomyField` (and its type `oneOf`), `piiMetaField` (and its `oneOf`), `piiReservedFieldConfig` (string-only), `eventKeyConstraints`, and `portableCheck` (only portable constraint keywords).
5. **Shared definitions** (`format`, `scalar`, `checks`) live once in `field.schema.json#/definitions`; reference them. A new fixed-shape object gets `patternProperties {"^x-": {}}`, `additionalProperties: false` and the `x-opentp` `not`.
6. **Validator support.** Use only keywords from the subset, or extend `validate()` and add a test.
7. **Docs:** `docs/schema/events.md` (the field table and constraints), `docs/schema/opentp-yaml.md` (taxonomy constraints, catalog notes), `docs/semantics.md` (merge, presence, predicate, validator-only rules), README if it is a headline feature.
8. **Examples and tests.** Use the keyword in `examples/full` (or `simple` if it is core), and add a negative test for a misplaced use.
9. **Changelog.** Add it under `## [Unreleased]` with a migration note if old files change meaning.
10. **Checks and downstream.** Run the checks. List CLI support (opentp-cli `src/types/index.ts`, the merge in `src/core/payload.ts`, `src/core/validator.ts`) as a follow-up.

### Add or modify a doc page
1. Put the page under `docs/` and start it with exactly one `# Title`. The website sync takes the Starlight title from the first H1, unless the page is in its explicit `add_frontmatter` list.
2. Link the page from `docs/index.md` and from the README "Documentation" list (and from `docs/schema/index.md` for schema pages). The website must also add the page to the explicit sidebar in `opentp-website/astro.config.mjs`.
3. YAML fences:
   - use a plain ```` ```yaml ```` fence;
   - full-file blocks are schema-validated; use them for anything that claims to be a complete file;
   - check fragments against the right pointer (see "Checking doc fragments");
   - mark deliberately wrong examples with `<!-- invalid: <expected error> -->` on the line before the fence.
4. Use relative links that start with `./` or `../` (they work on GitHub and are rewritten for the website). Run a link check after renaming a heading: anchors are GitHub slugs (the heading "Derived versions (`$ref`)" becomes `#derived-versions-ref`).

### Cut a new spec version `YYYY-MM`
In this repo:
1. Set `$id` in all 5 schemas to `https://opentp.dev/schemas/YYYY-MM/...`, and the `const` and `examples` in `version.schema.json` (`checkSchemas` fails until all of them agree).
2. Replace `opentp: <old>` in every example and every Markdown block, including fragments: `git grep -n "<old>" -- . ':!CHANGELOG.md' ':!AGENTS.md'`. Update the README "Specification Version" section, "Format Version" in `docs/index.md`, and the version rows in the docs reference tables.
3. Rename `## [Unreleased]` in `CHANGELOG.md` to `## [YYYY-MM] - <tag date>`, with the Breaking/Relaxed/Added/Removed lists and a "Migration from <old>" table.
4. Update this file: the Status table, the `$id` example under "Format model", the tag list in the "Never move... a published tag" rule. In the local workspace, also update the "Spec version" line in `../AGENTS.md`.
5. Run the checks. Commit, then create and push an **annotated** tag, only when the user asks: `git tag -a YYYY-MM -m "OpenTrackPlan YYYY-MM" && git push origin main YYYY-MM`. Watch the `Release` workflow; never re-point the tag afterwards.

Cross-repo order (details: `../opentp-website/AGENTS.md` and `../opentp-cli/AGENTS.md`):
1. Spec tag pushed and the GitHub Release published (step 5 above).
2. jsDelivr serves it: `curl -s -o /dev/null -w '%{http_code}\n' https://cdn.jsdelivr.net/gh/opentrackplan/opentp-spec@YYYY-MM/schemas/opentp.schema.json` prints `200`.
3. Website: add the static `/schemas/YYYY-MM` and the dynamic `/schemas/YYYY-MM/*` rules (to `@YYYY-MM`) above `latest` and the catch-all. This is safe to deploy right away.
4. CLI release with the new `specVersion` and `opentp migrate` (the CLI accepts exactly one version).
5. One website push that repoints `/schemas`, `/schemas/latest`, `latest/*` and the catch-all to the new tag, resyncs the docs, and updates the landing sample in `src/pages/index.astro`.
6. Smoke-test every `$id`, e.g. `curl -sSL https://opentp.dev/schemas/YYYY-MM/opentp.schema.json | grep -F '"$id"'`.

Pushing opentp-website `main` is the production deploy (Cloudflare Pages Git integration). `astro dev` and `astro preview` ignore `_redirects`, so verify on a Cloudflare preview deploy or after the deploy. If `latest` moves before step 4, users who follow the `latest` modelines in these docs are pushed to a format that the released CLI still rejects.

### Downstream invariants
- **opentp-cli** (public): it never loads this repo's schemas, so every schema and semantics rule is reimplemented by hand. It accepts exactly one `specVersion`, rejects any other `opentp` value, and ships `opentp migrate` for the previous version. Steps: `../opentp-cli/AGENTS.md`.
- **opentp-website** (private): `_redirects` needs one rule per version that appears in any `$id`; `src/content/docs/docs/spec/` holds synced copies of `docs/`. Steps: `../opentp-website/AGENTS.md`.
- **opentp-sdk** (public `@opentp/sdk` 0.1.0, TypeScript runtime SDK; not checked out locally): no direct dependency on this repo is known.

## Known issues & traps (verified 2026-10-03)

- **`2026-09` is not tagged yet.** Until the tag exists and the website has a `2026-09` rule, `https://opentp.dev/schemas/2026-09/*` does not resolve, and the `latest` modelines in these docs serve the 2026-01 schemas, which reject every 2026-09 file.
- **The schemas cannot check everything.** Closed vocabulary, inherited types (and the type-dependent keywords of event fields that inherit their type), the merge rules, presence across layers, policy, dictionaries, code-facing names and overlap are validator-only rules. `validate.ts` never merges layers, so an example can pass it and still fail the CLI: reason through the rules (or run the CLI) when you change `examples/full`.
- **No real JSON-Schema engine in CI.** The checker implements a subset by hand; an Ajv cross-check is planned (workspace ROADMAP item 6). The schemas use only draft-07 keywords, the canonical meta-schema URI, and no `$ref` siblings, so Ajv 8 should accept them, but this is not tested.
- **Fragments are checked by hand** (47 of 54 blocks). A fragment that is wrong but parses passes CI.
- **Older tags are frozen as published:** `2025-06` through `2026-01` declare the non-canonical `$schema` `https://json-schema.org/draft-07/schema#` (Ajv 8 with defaults fails on it) and do not pin their version, so they accept files of other versions.
- **Masker id `star`** is called "built-in" in `docs/schema/events.md`, but no tool implements masking.

## Definition of done

- [ ] Schemas, docs (`docs/`, including `semantics.md` when behaviour changes), examples, `README.md` and `CHANGELOG.md` describe the same format; terminology matches everywhere:
  - catalog / common fields / event layer; `policy` (`specified`, `restricted`, `fixed`);
  - `template` (paths, composite fields) vs `pattern` (regex);
  - `checks`, `spec.checks`, tool-defined check ids;
  - `pii.kind`/`pii.masker`;
  - `current`, aliases, `$ref`, `<payloadKey>::<versionKey>`.
- [ ] Shared definitions are referenced, not copied (`format`, `scalar`, `checks`), and every mirror is updated (taxonomy, pii, key constraints, portable checks).
- [ ] New schema keywords are within the validator subset, or `validate.ts` is extended with a test. A rejection of misuse is a test in `scripts/validate.test.ts`.
- [ ] New or changed doc YAML fragments are checked against their schema pointer; deliberately invalid blocks carry the `<!-- invalid: ... -->` marker. Full-file blocks parse and validate.
- [ ] `bun scripts/validate.ts` exits 0 and `bun test scripts/validate.test.ts` passes (Bun 1.4.2, after `bun install --frozen-lockfile`).
- [ ] Optional: the reference CLI validates `examples/simple` and `examples/full` with no errors and no warnings, and `examples/extensions` with only the `mytool.*` unknown-check warnings.
- [ ] No published version is changed; the change is recorded under the next version in `CHANGELOG.md`. No published tag is moved.
- [ ] Downstream follow-ups are listed for opentp-cli and opentp-website ("Downstream invariants").
- [ ] Nothing was committed, tagged or pushed without the user asking. The commit message is in English.
